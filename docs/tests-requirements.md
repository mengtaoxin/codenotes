# 测试规范

本仓库的测试服务于**个人学习**：失败时要能快速看懂「输入是什么、期望什么、实际得到什么、哪里不对」，而不是只知道「断言挂了」；对常见算法，测试集本身也要够用，别只靠一两条 happy path。

## 失败信息要对人可读

检测出错误是底线；**让人一眼能定位问题**才是目标。

写用例或断言时，失败输出至少应能回答：

1. **调用前的输入**是什么（不要只剩期望/实际两侧 diff）
2. **期望结果**是什么
3. **实际结果**是什么
4. **差异在哪**（例如数组下标、引用是否同一对象、长度是否一致）

避免只写裸的 `expect(actual).toEqual(expected)` 就结束——默认 diff 往往丢掉上下文（尤其是排序：看不到原始未排序输入时很难对照算法逻辑）。

优先复用或扩展 `toolings/` 里的可读断言（如排序的 `expectSorted`），而不是在每个用例里堆一长串 `expect`。`algorithms-tests/` 只放测试用例。

### 反例 / 正例（排序）

反例：失败时只有两侧数组 diff，看不出当初传入的未排序序列。

正例：失败信息类似：

```text
排序结果不符合预期

输入（调用前）: [3, 1, 4, 1, 5, 9, 2, 6]
期望输出:       [1, 1, 2, 3, 4, 5, 6, 9]
实际输出:       [1, 3, 1, 4, 5, 2, 6, 9]
首个差异下标:   1（期望 1，实际 3）
全部差异:
  [1] 期望 1 ≠ 实际 3
  ...
```

## 常见算法：测试集要丰富

排序、查找、图遍历这类**成熟经典算法**，不要只写「乱序能排对」一条就交差。很多错误实现能碰巧通过单一路径（例如已排序输入上「什么都不做」也会对）。

写/补测试前，优先对照网上已有的经典清单或开源实现里的用例（例如讨论排序如何测的文章、TheAlgorithms / 教材配套测试），按本仓库契约裁剪，而不是凭感觉只造一两个例子。

### 排序类最低覆盖（参考）

结合常见边界讨论与排序专项测试实践，至少覆盖：

| 类别 | 例 | 用意 |
| --- | --- | --- |
| 退化边界 | `[]`、`[x]` | 「什么都不做」也要正确（Kernighan & Pike 边界思路） |
| 最小非平凡 | `[2,1]`、`[1,2]` | 最小交换 / 已有序二元组 |
| 顺序形态 | 已排序、逆序、一般乱序 | 挡住「空实现」「只对某一形态碰巧正确」 |
| 重复值 | 含重复、全相等 | 相等分支容易写错比较符 |
| 数值范围 | 负数、零、正数混排 | 避免只在正整数上碰巧正确 |
| 契约相关 | 是否允许返回新数组、是否禁止改入参等 | 与实现约定一致即可，不必强行测原地 |

可选加强（有余力再加）：小数组全排列（如 `[0,1,2]` 的 6 种）、与语言内置 `sort` 对照、稳定排序用「键相同身份不同」的对象测相对次序。纯 `number[]` **测不出真正稳定性**，不要把「含重复能排对」写成 stable 测试。

其它经典算法同理：先列该算法的典型边界与对抗用例，再落成可读断言；宁可少而准地盖住类别，也不要堆一堆同质乱序。

## 一次只暴露一个失败

同一算法套件里用例按顺序执行；已配置遇第一个失败即停止（`bail: 1`）。修好当前错误再跑后续用例，避免一次刷出多条失败干扰阅读。
